# API·3D 연결 기준

상위 [API 문서](../../docs/04-api-data.md), [3D 파이프라인](../../docs/03-3d-pipeline.md), 실제 [서버 스키마](../../backend/app/schemas.py)를 함께 확인한다. 아래는 Unity 구현을 위한 점검 기준이며 새 API 계약을 정의하지 않는다.

## API

- 실행 중인 서버의 `/openapi.json`과 실제 스키마를 확인해 C# DTO를 맞춘다. 필드의 JSON 이름·alias·null·열거형·날짜·배열 형식을 검증한다.
- PRD의 예정 API와 현재 서버 구현을 구분한다. 빠진 엔드포인트·필드와 충돌은 해당 이슈에 적고 서버 담당자와 합의한다.
- 인증은 설계상 Supabase OTP REST 직접 호출, 앱 API는 토큰 전달·서버 검증이다. Gemini·Meshy 비밀 키와 Supabase service role 키는 앱에 넣지 않는다.
- 토큰은 기기 보안 저장소에 둔다. PlayerPrefs 평문 저장을 하지 않는다. 인증 헤더·서명 URL·사용자 자료를 로그에 노출하지 않는다.
- 생성 요청은 idempotency key를 사용한다. 같은 요청의 재전송과 새로운 생성 시도를 구분하고 앱 재시작 후에도 기존 작업을 조회한다.
- 상위 설계의 작업 조회 간격은 3초다. 종료·취소·화면 이탈 시 불필요한 조회를 정리하고 네트워크 실패를 생성 실패와 구분한다.
- `jobId`, `queued/running/succeeded/failed`, 결과·오류 형식은 실제 응답과 대조한다. 성공 응답만으로 필요한 파일까지 정상 로드됐다고 판단하지 않는다.
- GLB·이미지는 비공개 버킷의 만료되는 서명 URL을 사용한다. 만료 후 갱신 방법이 미정이면 차단 사항으로 기록한다.

## 목 응답

목과 실서버는 같은 클라이언트 계약으로 교체 가능하게 한다. 개발용 목 사용 여부는 개발 설정·검증 기록에서 식별한다. 목 통과를 실서버 통합 완료로 보고하지 않는다.

최소 시나리오는 정상 완료, 진행 중, 네트워크 실패, 서버 작업 실패, 중복 탭, 앱 재시작 복구다. 등록·동의·확정 상태와 만료 URL도 해당 기능 구현 시 검증한다. 미정 계약을 목 응답으로 조용히 확정하지 않는다.

## GLB·관절·애니메이션

- 정리된 메시 규격: 정면 +Z, 바닥 y=0, 키 1 정규화. Blender·glTF·Unity 사이 축 변환은 임포터 동작을 확인해 한 번만 적용한다.
- 왼쪽 관절 10개와 `skeletonVersion`은 서버 스키마 기준이다. 오른쪽은 규격상 x 부호를 뒤집어 만든다. 실제 Unity 로컬·월드·정규화 좌표를 구분한다.
- 표준 뼈 이름·계층·로컬 축은 버전으로 고정한다. `docs/skeleton-spec.md`가 실제로 제공되었는지 확인하고, 없으면 임의로 최종 규격을 만들지 않는다.
- glTFast 로드 결과, 스킨·머티리얼, Animator 바인딩, 체형 보정 후 클립 동작을 테스트용 리깅 GLB로 확인한다.
- 단순 모델 표시와 공용 애니메이션 바인딩 성공을 별도 결과로 기록한다. 애니메이션이 없는 GLB를 로드했다고 리깅 검증 완료로 표시하지 않는다.
- F07 앱 범위는 보정 관절 제출·리깅 상태·결과 표시다. 자동 웨이트와 Blender 헤드리스 실행은 별도 담당 작업이다.

## 외부 의존성 기록

각 이슈에 제공자, 필요한 파일·API, 규격 버전, 준비 상태와 목 대체 가능 범위를 적는다. 실제 연결 가능성을 확인하기 전에는 담당자 일정이나 PRD에 예정된 파일을 제공 완료로 간주하지 않는다.
