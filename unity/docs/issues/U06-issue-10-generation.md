# U06 / #10 — 4면 확인·생성 진행·이어하기

- 작업일: 2026-10-30. 이슈: [#10](https://github.com/2-changmin/withme/issues/10), CLOSED(COMPLETED), 2026-10-30 종료.
- 사용자 지시: 제공한 4면 PNG·GLB를 목 서버로 연결. 실제 Gemini·Meshy 호출, 새 APK, 리깅·걷기 구현은 이번 범위에 포함하지 않는다.
- 상태: 구현·목 HTTP/PC 검증 완료. 사용자 직접 확인·실서버 생성·Android 검증은 미실행.
- 종료 근거: `b7923599`를 unity에 푸시한 뒤 최신 완료 조건 3개와 구현·검증 기록을 대조해 체크했다. [종료 댓글](https://github.com/2-changmin/withme/issues/10#issuecomment-6518901170)에 목 서버·PC 검증과 실제 생성·Android 미검증 범위를 구분했다.

## 구현

- 기존 Start 씬과 #9 `UploadsReady`에 연결했다. 미디어 ID를 받고 4면 생성 요청→3초 작업 조회→보호자 확인→3D 요청→GLB 로드 순서로 진행한다.
- ‘사진 속 모습을 찾고 있어요’, ‘당신의 강아지가 맞나요?’, ‘네, 우리 아이가 맞아요’, ‘다시 찾아보기’를 사용한다. 재생성은 최초 생성과 별도로 최대 3회이며 서버 429도 처리한다.
- 원본과 4개 이미지를 표시하고 확대한다. API의 방향 매핑이 불완전하므로 ‘사진 1~4’로 표시한다. 목 결과의 순서는 side/front/back/other다.
- 생성 상태는 queued/running/succeeded/failed, 진행률은 단계별 0~100이다. 완료 후 실제 에셋을 읽는 동안은 ‘모습을 불러오고 있어요’로 구분한다.
- GLB를 glTFast로 읽어 전용 카메라·RenderTexture에 표시하며 회전 버튼을 제공한다. `ModelReady`·`CharacterModelId`가 후속 단계 연결점이다. 미확정 모델은 3D 방에 진입하지 않는다.
- 첨부 GLB에는 메시 1개, 스킨 0개, 애니메이션 0개다. 정지 모델 검증이며 걷기 완료를 의미하지 않는다.

## 목 서버

저장소 루트에서 실행한다.

```powershell
python unity/tools/generation-mock-server.py
```

- `127.0.0.1:8765`에만 바인딩한다. 생성 요청에는 `Bearer demo-access`만 허용한다. 실제 계정 토큰·사진 업로드·외부 생성 API를 사용하지 않는다.
- 기본은 골든 4면과 제공 GLB다. `--fixture maltese`는 4면만 말티즈로 바꾸며 GLB는 골든 샘플 그대로라 일치하는 생성 결과로 취급하지 않는다.
- `--duration 6`은 작업 시간 연출, `--fail LIMIT_EXCEEDED` 또는 `--fail UPSTREAM_FAILED`는 실패 재현이다. 별도 포트는 `--port 8766`으로 실행한다.
- 서버 작업은 프로젝트 `Temp/generation-mock-state*.json`에 남는다. 이 파일이 없어지면 목 서버 작업 복구는 불가능하다. 클라이언트/서버 기록을 임의로 초기화하는 버튼은 만들지 않았다.
- Start 씬의 `LoginFlow.useDemoResponses`를 사용자 요청에 맞춰 켰다. 임의 이메일·코드 `123456`으로 목 로그인한다. 화면에 ‘목 서버 확인용·실제 AI 생성 없음’을 표시한다. 최초에는 첨부 샘플 중 사진을 골라 #9 목 등록→안내 확인으로 진행한다.
- 로컬 HTTP 허용은 Editor에서 명시적으로 켠 경우의 루프백 주소에만 한정된다. 제품 연결은 HTTPS이며 실제 로그인 토큰을 로컬 목 서버에 보내지 않는다.

## 저장·복구와 실패

- 앱의 `persistentDataPath/Generation/{fixture-v1|live-v1}/{userId}.json`에 사용자·반려견·미디어·작업 ID, 단계, 미처리 동작과 요청 키를 저장한다. 서버/목 환경을 분리한다.
- 요청 의도와 키를 먼저 기록하고 POST한다. 응답 유실·앱 종료 후 같은 키/참조 ID로 재개한다. create/approve는 Idempotency-Key, retry는 같은 referenceViewId에 대한 서버 중복 방지 계약을 사용한다.
- 서명 URL·에셋 바이트·앱 토큰은 복구 JSON에 넣지 않는다. 재개할 때 작업·미디어를 GET해 URL을 새로 받는다. JSON은 임시 파일 작성 후 교체하고 읽을 때 사용자·버전·ID·단계를 검증한다.
- ‘나중에 이어하기’·사진 모드·앱 일시 중단은 클라이언트 조회/다운로드를 취소하며 서버 작업을 취소하지 않는다. 재접속·복귀 시 기존 작업 조회로 이어간다. 로그아웃/사용자 변경 시 화면·메모리를 정리하고 다른 사용자 기록을 사용하지 않는다.
- 연결 실패와 작업 실패를 구분한다. 서버 작업이 failed여도 새 유료 작업을 자동 생성하지 않는다. 크레딧/횟수 제한은 재시도를 차단하고 사진 모드로 안내한다.
- 사진 모드는 저장한 원본 mediaId를 조회해 다시 읽는다. 원본 파일을 새 생성 결과로 덮어쓰지 않는다. 파일 다운로드에는 앱 인증 헤더를 붙이지 않고 리디렉션을 금지한다.

## 검증 도구

- `verify-generation.cs` / `VerifyGeneration.Run`: 요청 전 기록·응답 유실 동일 키 재개·상태 검증·재생성 한도·확인 후 생성·실패 중복 요청 없음·사용자 격리·URL 미저장.
- `verify-generation-view.cs` / `VerifyGenerationView.Run`: Play에서 #9 목 업로드부터 로컬 HTTP 4면·확대·재생성·사진 모드·실제 포인터 확인·GLB 표시까지 검증.
- `ResumeAfterRestart`: Play 종료·재시작·목 재로그인 후 완료된 같은 모델 작업 복구.
- `PreparePending`→Play 종료·재시작→`ResumePending`: 진행 중 기록의 같은 작업을 조회해 4면 확인 화면으로 복구.
- `Failure`: 8766 포트에 `--duration 1 --fail LIMIT_EXCEEDED` 서버를 실행한 뒤 한도 실패·재시도 차단·원본 사진 모드를 검증한다.
- 검증 도구는 앱 임시 경로에 별도 복구 기록을 사용한다. 사용자 기본 작업 기록과 분리한다.

## 한계

- 현재 작업/전체 작업 목록 API가 없어 앱 데이터 삭제·재설치·다른 기기의 전체 복구는 보장하지 않는다. 서버 재생성 잔여 횟수도 응답에 없어 이 기기의 알려진 횟수와 서버 한도로 제어한다.
- 배포 API와 같은 요청/작업 계약을 연결했지만 이번 검증은 로컬 목 서버다. 실제 생성 품질·Meshy 비용 차단·Blender·Android 저장 및 복귀는 검증하지 않았다.
- 자동 움직임 준비·‘움직임이 어색해요’·외형 수정·최종 확정·습관·3D 메인은 후속 이슈다.
- APK는 사용자 지시로 보류, 이번 작업에서 생성하지 않았다.
